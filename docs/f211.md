# f211 — seek 分段、音画同步、零拷贝回归与默认路径决策

本篇记录 f211 的实测：Media Foundation 零拷贝解码（f209 接入）之后的 **seek 端到端
延迟**、**音画同步**、**五个入口 / 换档 / 暂停恢复 / 回退** 的回归，以及据此做出的
**默认解码路径决定**。

复现脚本（都在 `scripts/`）：

| 脚本 | 作用 |
| --- | --- |
| `qa-f211-seek.ps1` | 20 次真实 seek（`BILI_SEEK_AT`，走 `PlaybackControl::seek`），写 `seek trace` / `seek served` |
| `qa-f211-avsync.ps1` | 一次跑完 播放 / 暂停恢复 / seek / 换档 四个相位，10 次/秒采样 `delta_ms` |
| `qa-f211-entries.ps1` | 五个入口各一遍（`vod` / `live` / `pgc` / `fish` / `search`） |
| `qa-f211-shots.ps1` | 两张验收截图 `docs/f211_seek.png`、`docs/f211_avsync.png` |
| `qa-f211-report.py` | 把上面的日志算成表（seek 分段 + p50/p95、`delta_ms` 分布、换档） |

日志在 `target/qa/f211/`。

## 1. seek：900 ms 花在哪，改完是多少

### 1.1 先加分段打点

`seek served first_frame_ms=…` 只说**多久**，不说**花在哪**。f211 在
`PlaybackControl` 里加了一条分段时钟（`SeekSegments`），在真正的阶段边界打点，
一次 seek 输出一行：

```
seek trace kind=mf-inplace total_ms=39 ui_ms=2 teardown_ms=- setup_ms=- decoder_ms=26 audio_ms=- present_ms=11 ring=16
```

六段（`-` = 这个 seek 没经过这一段）：

| 段 | 从 → 到 |
| --- | --- |
| `ui_ms` | 释放（`PlaybackControl::seek`）→ pacer 察觉 |
| `teardown_ms` | 旧会话：杀解码器、join reader、停音频 |
| `setup_ms` | 新会话：取流 / 选轨 / 定尺寸 |
| `decoder_ms` | MF `SetCurrentPosition`（或 ffmpeg 起进程） |
| `audio_ms` | `ffplay` 在新位置起来 |
| `present_ms` | 第一帧上屏 |

### 1.2 原来的 900 ms 是两块，不是一块

| 场景 | 断点 | 实测 |
| --- | --- | --- |
| 工厂默认（画面直出 **关**，winit） | `start_mf_session` 先等 DComp 视频层 900 ms，等不到才回退 ffmpeg | 起播 `first present 2467 ms` → 改后 **1505 ms**（−962 ms） |
| 画面直出 **开**、MF 生效 | seek 走"整会话重启"：teardown + 重新取流 + `ffplay` 重起 + 首帧预卷 | 端到端 **p50 85 ms / p95 174 ms**（同一台机器） |

ffmpeg 管道路径（`BILI_DECODE=ffmpeg` 或 winit）不走 MF，seek 走 f151 的
**预滚影子**（`SeekShadow`），实测 p50 ≈ 517–535 ms，与改动前一致。

### 1.3 改了什么

1. **MF 只在画面直出开着时尝试**（`start_mf_session` 开头一行判断）。winit 路径没有
   视频层、也没有可写的设备，原来每个会话白等 900 ms（起播和每次硬重启各一次）。
   现在一次都不等，日志一行 `decode fallback reason=no_dcomp_platform (画面直出 off)`。
2. **视频层等待改成"有结论就结束"**：`prime_video_layer` 把结果写进
   `FrameMailbox::prime_state`（0 未定 / 1 已发布 / 2 这窗口没有），`start_mf_session`
   等这个结论而不是盲等固定时间——层被建起来的瞬间就走，明确没有就立刻回退。
3. **MF 下的 seek 原地做**（`start_inplace_seek` + pacer 里的一条分支）：`mf_seek`
   只是 flush + `SetCurrentPosition`（实测 **0.9–4.9 ms**），重启整个会话却在它外面
   又付了 teardown、重新取流、`ffplay` 起来和首帧预卷。现在：

   * 解码器原地 reposition，pacer 的时间线 / 显示栅格直接从新位置继续（`frames=0`、
     `start_ms=target`），不结束会话；
   * 声音的旧进程随画面一起停，**新进程在第一帧上屏之后才起**（`ffplay` 的
     spawn 不再挂在 seek 的关键路径上）；
   * 释放时关上的 mailbox 闸门在 sink 就位时打开，而不是等一整个新会话；
   * 有兜底：解码器 1.2 s 内不报就位、或 3 s 内没有画面，就退回原来的重启路径
     （只会更慢，不会卡死）。`kind=` 会写 `mf-inplace` / `mf-seek` / `mf-open` /
     `shadow` / `ffmpeg`，一眼能看出这次 seek 走的哪条。

4. `has_pending_seek()` 也进了 120 Hz 的 slot 循环：释放后不再把这一帧剩下的 3 个
   显示槽跑完（30 fps 下最多 25 ms 的"用户已经不要了的画面"）。

结论：**p50 39 ms ≤ 50 ms 达标**，p95 77 ms。剩下的结构性下限是
`decoder_ms`（MF 自己的 flush + `SetCurrentPosition`，8–78 ms，中位 ~20 ms）和
`ui_ms`（pacer 一帧一次的节奏，0–33 ms）；两者都不在播放器的调度里，没法再压到
个位数。**每一次 run 的第一次 seek 在 140–280 ms**（首帧时 sink 的 warp 管线/合成器
刚起来，`ui_ms` 记到 110–170 ms），这是冷启动成本，不是稳态。

冷目标（本地缓存没有、要走网络）不在此列：`decoder_ms` 740 ms 级别，网络取 GOP 的
时间，结构性下限就是 RTT + 码率 × 关键帧间隔。

## 2. 音画同步

采样器是 `src/qa/f211.rs`（`BILI_AVSYNC_TEST=<tag>`）：一个独立线程，10 次/秒，读的是
UI 也读的两个已发布位置——`presented_ms`（在屏那一帧的 pts）和 `audio_clock_ms`
（`ffplay` 报的位置）。`delta = 音频 − 画面`，正值 = 声音在前。

相位由播放器自己打标（`avsync_phase`），窗口 3 s：

* `play` 稳态；
* `resume` 暂停 2.5 s 后恢复；
* `seek` 一次真实 seek 之后；
* `switch` 一次真实画质切换之后。

`target/qa/f211/f211_avsync_mf_dc1_main.log` + `f211_shot_avsync.log`
（两次独立 run，各 40 s 左右，pause 与 seek 的时间点不同）：

| 相位 | n | p50 | p95 | min | max |
| --- | --- | --- | --- | --- | --- |
| play | 249–265 | 17–20 | 33–35 | 0–1 | 35–42 |
| resume | 29 | 18–22 | 41–94 | 1–2 | **107–196** |
| seek | 12–25 | 14–23 | 32–34 | 1–4 | 33–35 |
| switch | 15–20 | 12–18 | 29–34 | 2–4 | 31–34 |

读法：

* 稳态 **p50 ≈ 18 ms、p95 ≈ 33 ms、max ≤ 42 ms**：在 ±30 ms 的 p50 目标内，p95 略高于
  30 ms。这个 +18 ms 的基线是系统性的：`presented_ms` 是交给 sink 的**那一帧**，真正
  扫出要再等一个显示周期（120 Hz = 8.3 ms），再加上 `ffplay -stats` 的 100 ms 报数
  granularity——不是漂移，也不是累积的。
* `seek` 与 `switch` 之后 **都在 30 ms 上下收敛**，没有一个样本超过 35 ms。
* `resume` 的前 1–2 个样本会冲到 **107–196 ms**（三次 run 的最大值分别是 92 / 183 /
  196 / 107 ms）：被 `NtSuspendProcess` 挂起的 `ffplay` 恢复时，设备时钟先把挂起期间
  的时间记进去，随后 `avsync` 看着它收敛回 ≤35 ms。
  这是"暂停恢复"这一相位的真实代价，不是稳态误差——A/V 守卫没有为它重启音频，因为
  一帧之后偏差就回到窗口内。

## 3. 五个入口 + 换档 + 暂停恢复 + 回退

| 入口 | 日志 | 结论 |
| --- | --- | --- |
| 点播 | `decode=mf hw=1 size=1920x1080 fps=30.00 open_ms=933`，`startup first present t=1357ms` | **通过**：零拷贝，首帧 1.4 s，A/V delta 26 ms |
| 直播 | `live spawn ffmpeg 720x1280 kind=flv`，`live-test room first_frame_ms=3157` | **通过（不经 MF）**：直播有自己的 ffmpeg 拉流管线，从不进 `player::spawn`，所以 MF 既不会尝试也不需要回退；画面/日志与改动前一致 |
| 番剧 | `decode=mf hw=1 size=1920x1080 fps=25.00`，`pgc-test card-first-frame`，首帧 1682 ms | **通过**：零拷贝（25 fps 源） |
| 养鱼 | `fish feed sort=…`、`fish watch tiers` 正常；本次配置（`fish_enabled=false`，无模型）不触发看片 | **通过（页面）**：养鱼看片走 `fish_wiring::open_player_for`，与点播同一个打开/解码路径，不另建解码器 |
| 搜索 | 第一次打开：MF 会话没起来 → `decode fallback reason=no_dcomp_video_sink timeout` → ffmpeg 播放，首帧 1910 ms | **不通过（MF 未起来，已自动回退）** |

**换档（5 次 pick，4 个实际档位）** `target/qa/f211/f211_quality.log`：

| pick | qn | 结果 | `switch_after_ms` | `decode` |
| --- | --- | --- | --- | --- |
| 1 | 80 | already-current（当前就是 1080P） | – | – |
| 2 | 64 | matched=1 | 227 | `decode=mf … size=1280x720 open_ms=878` |
| 3 | 32 | matched=1 | 146 | `decode=mf … size=852x480 open_ms=57` |
| 4 | 16 | matched=1 | 1067 | `decode=mf … size=640x360 open_ms=969` |
| 5 | 80 | 再次 pick 80，已切回 1080P | 1017 | `decode=mf … size=1920x1080 open_ms=910` |

没有黑屏（每次都有 `session first present … matched=1`）、没有卡死、`stream qn=` 与
`decode=mf` 一一对应。换档耗时 146–1067 ms，主要就是新 URL 的一次 `mf_open`
（878–969 ms）——换档换的是流，会话必须重建，这一项没法原地做。

**暂停 / 恢复 / 遮挡 / 缩放全屏 / 关闭重开**：

* 暂停 → 恢复：`pause-at resume=0/1`，`resume` 相位 ≤35 ms（除了上面说的 1–2 个
  165–196 ms 的瞬态），没有重启解码器。
* 遮挡暂停 / 全屏 / 缩放：走的是 UI 属性 + 播放器既有的 `pause hold` / 布局路径，
  f209 之后没有改动，`BILI_F152_TEST` / `BILI_FULLSCREEN_TEST` 的既有回归仍然覆盖。
* 关闭重开：**这一项 MF 没通过**——同进程里关掉再开一个新窗口（搜索入口的连接打开
  也是这样）时，新窗口的 DComp 视频层没有在等待窗口内建立/发布，播放器按设计回退
  ffmpeg（画面正常，起播多约 0.9 s）。根因在 `src/dcomp` 的视频层发布时机（新窗口
  首帧之前不会建立），不在解码器选择，也不在播放器的会话管理。

**强制回退**：`BILI_DECODE=ffmpeg` 时 `mf_decode_enabled()` 直接为 false，日志里
一条 `decode=mf` 都没有，seek 走 f151 预滚影子（p50 535 ms / p95 632 ms），与改动前
完全一致；画面、换档、暂停恢复都不受影响。另一个逃生阀是把 `settings.json` 的
`player_mf_decode` 设为 `false`。

## 4. 默认路径的决定

**决定：零拷贝解码保持 opt-in（`player_mf_decode` 默认 `false`），不设为默认。**

理由（按"任何一项不通过就保持 opt-in"的规则）：

1. **只差一项**：搜索入口 / 同进程关闭重开时 MF 会话没有按时起来，播放器自动回退
   ffmpeg。画面是对的、用户能看，但起播多约 0.9 s，且这一项无法在
   `src/player.rs` 里修（视频层由 `src/dcomp` 在新窗口上发布）。
2. **它本来就需要画面直出**：`player_dcomp` 出厂是 `false`，零拷贝没有可写的设备。
   也就是说即便把 `player_mf_decode` 默认打开，工厂配置下它也不会运行——"默认开的
   零拷贝"是个假象。
3. 开着的时候它确实更好：1080p 零上传（`upload_bytes=0`）、120 fps、seek p50 39 ms。
   这些都是"值得打开"，不是"必须默认打开"。

怎么打开：

```jsonc
// settings.json
"player_dcomp": true,      // 画面直出（必须，重启后生效）
"player_mf_decode": true   // 零拷贝 + GPU 光流 120 帧
```

或按次：`BILI_PLAYER_DCOMP=1 BILI_DECODE=mf`。
逃生阀：`BILI_DECODE=ffmpeg`（任何时候都能退回 ffmpeg 管道）。

UI 里现在写明了这层依赖（`ui/app.slint` 的画面直出行）：

* 开：`画面直出：开启（零拷贝 120 帧）`
* 关：`画面直出：关闭（零拷贝 120 帧需开启）`

### 不通过项的复现

```powershell
# MF 起不来的那个：搜索入口连着打开两个播放器窗口
$env:BILI_PLAYER_DCOMP=1; $env:BILI_SEARCH_TEST="原神"; $env:BILI_SEARCH_LOOP="2,9000,player"
.\target\release\o11a1.exe

# 日志里会看到
#   decode fallback reason=no_dcomp_video_sink timeout
#   （新窗口没有 dcomp video layer frame=… 这一行）
```

修好它的方向（属于 `src/dcomp`）：新播放器窗口的第一帧之前就把视频层建好，或者让
`prime_video_layer` 在窗口尚未就绪时返回"稍后"而不是让上层等满一个超时。
