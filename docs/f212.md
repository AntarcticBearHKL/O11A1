# f212 — 两个入口拿到视频层、默认打开零拷贝、恢复基线

本篇记录 f212 的两件事：

1. **修掉 f211 的两个入口**（搜索入口进播放器、同进程关掉再开）：它们拿不到 DComp
   视频层，自动回退 ffmpeg，起播多约 0.9 s。
2. 修掉之后**把「画面直出」和「零拷贝解码」改成出厂默认**，并给出默认配置下的验收。
3. 顺手修 f211 报的暂停恢复 `delta_ms` 尖峰。

复现/验收脚本（都在 `scripts/`，日志在 `target/qa/f212/`）：

| 脚本 | 作用 |
| --- | --- |
| `qa-f212-entries.ps1` `-Kind search\|reopen -Rounds N` | 两个入口各 N 次（`src/qa/f212.rs`，`BILI_ENTRY_CYCLE`） |
| `qa-f212-accept.ps1 -Stage 1080\|720 -Seconds 60 -Panel` | **默认配置**下 60 秒、4× 插帧、逐秒三层 |
| `qa-f211-seek.ps1` / `qa-f211-avsync.ps1` / `qa-f211-entries.ps1` | seek / 音画同步 / 五连回归（f211 的脚本照用） |

---

## 1. 根因：不是"层没建"，是"UI 线程在忙"

f211 的结论是"新窗口首帧之前 `prime_video_layer` 没有结论"。实测**不是**这个：

```
dcomp prime post frame=1280x720 paints=15      ← 会话线程发出请求
ui stall ms=253                                 ← UI 线程被占住（打完日志才看见是 905 ms）
decode fallback reason=no_dcomp_video_sink timeout state=0 paints=15 waited_ms=905
```

`prime_state` 一直是 `0`（未定），`paints` 一直停在 15 —— 也就是说 **UI 线程在那
900 ms 里根本没回到事件循环**，`slint::invoke_from_event_loop` 的回调排不上队；
窗口本身没事，视频层也没问题（同一次运行里第一个窗口的 prime 是 0–7 ms 完成的）。

窗口创建时 UI 线程在做什么？搜索入口 / 关掉再开这两个场景都要**重新发布一屏卡片**
（`search tab ... thumbs patched`、`feed page=0 items=30`），实测占住主线程
0.3–1.3 s，偶尔 7 s（`ui stall ms=1277 / 7197`）。900 ms 的等待正好落在中间。

所以修法不是"更早建层"，而是**别把"UI 线程正忙"当成"这个窗口没有层"**。

## 2. 改了什么

### 2.1 一个不经过事件循环的"窗口已建"信号（`src/dcomp`）

`DcompPlayerWindow::create()` 在合成树建好之后，把 `(HWND, 窗口自己的身份)` 写进
`dcomp::attached`：

```rust
pub(crate) fn attached(hwnd: isize) -> bool   // 任意线程，一次 mutex + 线性扫
```

窗口是在**打开播放器的那次点击里**（UI 线程）建好的，所以会话线程问这个问题时答案
早已是 `true`——不需要等事件循环。窗口不是 DComp 窗口（winit 回退）时，会话立刻拿到
`false`，日志一行 `decode fallback reason=no_dcomp_window`，不再白等。

### 2.2 等层：等到有结论，而不是等满一个超时（`src/player.rs`）

`start_mf_session` 的顺序变成：

1. `control.window_hwnd()`（打开时由 `player_host` 写在 `PlaybackControl` 上）+ 2.1 的
   `attached()`：**没有这个窗口就直接回退**，0 ms。
2. 发出 `prime_video_layer`，然后：
   * `dcomp_sink()` 出现 → 用它；
   * `prime_refused()`（窗口没了 / 建层失败）→ 立刻回退，日志 `no_dcomp_video_sink`；
   * 两者都没有 → **继续等**，每 `PRIME_REPOST_MS`（250 ms）重新发一次请求（丢一次
     唤醒只损失一次重发，不是整个会话），上限 `PRIME_WAIT_MS` = 8 s。
3. 等超过 150 ms 就写一行 `dcomp prime slow waited_ms=…`，所以"这一次为什么慢"在日志
   里是看得见的，而不是悄悄回退。

为什么敢等：**ffmpeg 管道的画面也是这个 UI 线程画的**。UI 线程没回来的时候，回退
ffmpeg 也不会多出一帧，等的只是"这一秒钟没有画面"，而回退丢掉的是这个会话整条零拷贝
路径（f211 报的正是这个）。窗口真的拿不到层（设备建不起来）时结论是立刻的，8 s 这个
上限只有"线程永远回不来"才会碰到。

实测（故意按住 UI 线程 4 s：`-StallMs 4000`）：

```
f212 cycle ui stall begin ms=4000
dcomp prime post frame=1280x720 paints=2      ← 每 250 ms 一次，共 7 次
dcomp prime run after_ms=1546 paints=2
dcomp prime ok hwnd=6688740 build_ms=27 since_post_ms=1573
dcomp prime slow waited_ms=1575 paints=2 (UI thread was busy, layer reused)
decode=mf hw=1 size=1920x1080 ...            ← 还是零拷贝
```

### 2.3 释放顺序：HWND 复用与 join（`src/dcomp/player_window.rs`、`video.rs`）

* **HWND 会被系统复用**。旧窗口的 `Drop` 原来按句柄删 `WINDOWS` / `sinks()`，如果新
  窗口正好拿到同一个句柄，旧窗口的收尾会把**新窗口**的注册删掉——下一条 prime 就会
  得到"这不是一个活着的播放器窗口"。现在两处都按窗口身份删（`Weak::as_ptr` /
  `Arc::ptr_eq`），`attached` 也是按 `(hwnd, 身份)` 记的。
* `sink.close()` 会 join 视频线程，而视频线程可能正卡在一次 30 s 的 MF 字节流超时里
  （镜像坏掉时实测）。窗口收尾在主线程 join 它，就是"关掉播放器以后整个界面僵 27 秒，
  下一个窗口打不开"。新增 `VideoSink::close_detached()`：置关闭位 + 唤醒后**不 join**，
  设备/交换链/解码器仍然由那个线程自己释放；合成树随后摘掉视觉，DComp 的引用计数保证
  交换链不会变成野指针。实测收尾 `sink_ms=0–1 total_ms=11–19`。

### 2.4 默认值（`src/settings.rs`、`ui/app.slint`）

* `player_dcomp` 默认 **true**（`default_player_dcomp()`，`read_player_dcomp()` 也用它，
  所以"没有 settings.json"就是开着）。
* `player_mf_decode` 默认 **true**（f211 曾改回 false，理由已经不成立）。
* 逃生阀都保留：`BILI_PLAYER_DCOMP=0`、`BILI_DECODE=ffmpeg`、以及设置里的两个开关。
* 设置里「画面直出」那一行：开 = `画面直出：已开启（默认）· 零拷贝 120 帧`，关 =
  `画面直出：已关闭（可开启零拷贝 120 帧）`（不再说"需开启"）。

## 3. 两个入口：10 + 10

`qa-f212-entries.ps1`，**不设任何选择路径的环境变量**（默认配置），一个进程里连续
N 次「打开 → 停 4–4.5 s → ✕ 关闭」。

| 入口 | 结果 | 日志 |
| --- | --- | --- |
| 搜索（`-Kind search`：真搜索 → 点第一个结果的卡） | **10/10 `decode=mf`，0 次回退** | `f212_entry_search.log` |
| 同进程关掉再开（`-Kind reopen`：推荐流的卡） | **10/10 `decode=mf`，0 次回退** | `f212_entry_reopen.log` |

旁证（同一二进制、同一配置）：

* 故意按住 UI 线程 4 s（§2.2）：`dcomp prime slow waited_ms=1575`，仍然是 `decode=mf`；
* 网络坏的时候偶发的是**另一种**回退：`decode fallback reason=mf_open_timeout` /
  `MF 解码器: 打开视频流超时（30s）`（字节流，与视频层无关）——这两种在 f211 就有，
  本次没有改，也不再被算进"入口问题"。

### 3.1 一个仍然存在的、与层无关的现象（如实记录）

10 次一轮的脚本偶尔会在第 2–3 轮之后**不再有日志**，被脚本按预算杀掉：
`ui stall ms=7197` 之后整进程没有任何线程再写日志，`dcomp player visible=false` 之后
没有 `prefetch disabled reason=player closed`（即卡在关窗路径里，**不是**卡在建层）。
同一二进制上 10/10 的 run 是干净的（两份日志都在 `target/qa/f212/`），失败的 run 里
也**没有**任何 `no_dcomp_*`。这一节不归 `src/dcomp` 的视频层：从打点看是关窗里
`hide()` 之后、`control.close()` 之前的应用侧工作（布局持久化 / 模型发布）在极慢的一次
里没有回来。因为不在本次改动的文件范围内，只记录现象与日志，不做修改。

## 6. 暂停恢复的 `delta_ms` 尖峰

f211 报的是恢复后头 1–2 个采样冲到 107–196 ms。实测是**两个**东西叠在一起：

1. **时钟**：`ffplay` 挂起期间设备时钟没停，恢复后第一条 `-stats` 报的是"内容 + 挂起
   时长"（2.5 s 的暂停实测报 +2465 ms）。会话的时钟本来只对 **> 120 ms** 的前跳把它当
   设备读数丢掉，107–196 ms 这一段落在"按 2 % 速率慢慢纠"的支路上，于是真的成了新基线。
   现在**恢复静默窗（800 ms）里任何超过 40 ms 的前跳都是设备**，样本丢掉、时钟保持
   释放时重锚的内容位置，并写一行
   `audio clock resume baseline reset reported_ms=… kept_ms=… dropped_ms=…`
   （单元测试 `f211` 覆盖 629 ms 与 196 ms 两档）。
2. **画面**：暂停时画面停在那一帧，声音先起，于是"第一个动帧"之前的采样量的是**释放
   顺序**（声音领先冻结画面 49–151 ms），不是播放。`avsync` 采样器把冻结帧与释放后的
   第一个动帧当作新基线（最多丢 4 个采样），逐条写
   `avsync … resume baseline reset presented_ms=… dropped_delta_ms=…`，数值照样在日志里。

结果（同一 44 s 脚本，pause 2.5 s @12 s、seek→90 s、换档 qn=64）：

| 相位 | 前（f211） | 后（f212） |
| --- | --- | --- |
| play p50/p95/max | 17–20 / 33–35 / 35–42 | 17 / 33 / 36 |
| **resume max** | **107–196** | **33**（n=26，p50 16，p95 31） |
| seek max | 33–35 | 31 |
| switch max | 31–34 | 34 |
