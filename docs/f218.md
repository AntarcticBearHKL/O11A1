# f218 — 播放器窗口：闪烁根因、圆角、弥散皮肤

beta.7 报的三件事都在播放器窗口：视频闪烁、圆角变方、面板/工具栏/弹窗没有吃到
弥散壁纸。这一篇是三者的证据链和修法。

复现/验收脚本：

| 脚本 | 作用 |
| --- | --- |
| `scripts/qa-f218-flicker.ps1 -Stage 1080 -Interp 3 -Slots` | 40 帧亮度表 + 每槽 `f218 slot pts luma` |
| `scripts/qa-f213-trace.ps1 -Stage 1080 -Interp 3` | 老协议（`f213 slot`），与本仓库既有基线同口径 |
| `scripts/qa-f218-shots.ps1` | 四角放大图 + chrome 截图 |

## 1. 闪烁：不是 f213 的帧序翻转复发，是解码器表面被回收

f213 的 `views_flipped` 修复**还在**（`src/dcomp/video.rs`，beta.7 未动过那段），
trace 里 `flip=1` 从第一槽起一直成立，`pair` 单调递增，没有「同一 pair 正反各播一次」。
所以先排除了老 bug。

真正的证据是这次给 trace 加的 `pts` / `luma` 一对：`pts` 是这一槽**选中**的源帧时间，
`luma` 是这一槽**画出来**的 backbuffer 均值。用一个「每个源帧一个平坦亮度」的
ramp 样片（`geq=lum=8+8*mod(N,30)`，30 fps），两者本应对齐（luma = pts 处的亮度台阶）。

修之前，同一个 250 ms 窗口里：

```
f213 slot ms=266 ... pts=19833..20066 luma=0..255
```

`pts` 只走了 233 ms（8 帧），像素却铺满整个 1 s 的 ramp —— 画出来的不是选中的帧。
逐槽看更清楚：

```
f218 slot pts=19833 luma=205      <- 应为 205
f218 slot pts=19866 luma=214
f218 slot pts=19900 luma=223
f218 slot pts=19933 luma=56       <- 应为 227，差了约 19 帧
f218 slot pts=19966 luma=242
```

### 根因

`mediadec::mf` 交给 sink 的是**解码器纹理数组的一个 slice**，并只保留
`ID3D11Texture2D` + 子资源号（`IMFSample` 在 `read_frame` 返回前就释放了）。
释放 sample 等于把那个 slice 还给解码器池，解码器下一次 `ProcessOutput` 就会写进去；
而 sink 的 `pump` 一次**预读最多 4 帧**再 `choose()`，所以被选的帧在转换之前就可能
已经被后面的帧覆盖。trace 第一次读到的表面描述是：

```
f218 surface size=1920x1088 array=12   <- 池子 12 个 slice，约 0.4 s @30 fps
```

与「画面最多错位 ~0.4 s、逐槽随机」完全吻合。

### 修法（`src/dcomp/nv12.rs::SurfaceRing` + `video.rs::pump`）

sink 不再持有解码器的表面：每读到一帧，**立刻** `CopySubresourceRegion` 到自己
4 个 NV12 纹理组成的环形缓冲里（GPU 侧，30 次/s，1080p 每次约 3 MB，不碰 CPU 像素），
队列里放的是这份拷贝。队列深度同时被限制在 `SURFACE_RING - 1`，所以一个拷贝在被
`choose()` 之前绝不会被下一次拷贝覆盖（第一次 seek 的 400 帧预读也一样，落在目标
之前的帧本来就没有用）。

修之后，同一个 ramp 逐槽就是一条干净的台阶：

```
f218 slot pts=100 luma=0
f218 slot pts=133 luma=9
f218 slot pts=166 luma=19
f218 slot pts=199 luma=28
f218 slot pts=233 luma=37
f218 slot pts=266 luma=47
```

250 ms 窗口：`pts=19833..20066 luma=0..65`（8 帧 × 约 9 灰阶，单调）。

### 40 帧数据（`docs/f218_player_frames.txt`）

同一份二进制、`qa-f213-trace.ps1 -Stage 1080 -Interp 3 -Frames 40`（老口径，`PrintWindow(2)`）：

| | 亮度标准差 | 相邻帧差均值 | 相邻帧差最大 |
| --- | --- | --- | --- |
| beta.7（修前，本次会话实测） | 3.21 | 26.98 | 47.51 |
| f218（修后） | **1.35** | **23.84** | **29.09** |

ramp 逐槽顺序探针：修前 40 帧 `avg=158.66 std=76.59 diff_avg=99.40`，修后同一段
画面是一条单调台阶（std 在 ramp 上没有意义，所以用逐槽 `pts/luma` 对齐来判断）。

### 性能

没有退化：`video_s=119.9`、`dm_s=62.9`（1080p、4× 插帧、DComp 弹幕，同一份二进制）；
seek 首帧 `45 / 81 / 37 / 20 ms`（`qa-f211-seek.ps1`，7 个目标）。

### 残余：约 0.7 % 的 pair 仍会错一帧（同一个根因，权限外的最后一步）

逐槽统计（15 s、447 个 pair，ramp 顺序探针）：错位的 pair 从**修前的接近一半**降到
**3 个（0.7 %）**，而且全部是「往前错 ~12–16 帧」——正好是解码器池子（12）的量级。
剩下这一点不是 sink 侧能关掉的：`CopySubresourceRegion` 是**在**
`mediadec::mf` 把 `IMFSample` 放掉**之后**才排队的，而那个 MFT 有自己的一批输出
surface，sample 一放行它就可能立刻把同一 slice 写进下一帧。

真正的收尾在 `src/mediadec/mf.rs`（不在本次改动范围内）：`read_frame` 现在返回
`RawFrame { texture, subresource, .. }` 时把 `sample` / `buffer` 丢了；只要把
`IMFSample`（或 `IMFMediaBuffer`）一起带进 `RawFrame` / `MfFrame`（一个字段 +
`Interface::clone`），slice 在 sink 放掉它之前就不会被回收，这里的环形拷贝就可以
退化成「无拷贝」。这一条已写进交接说明。

网络流（真实码率、解码被带宽节流）上没观察到这类跳变：6 个 250 ms 窗口的
`luma` 区间是 `31..36 / 30..42 / 37..47 / 22..44 / 22..32 / 26..47`，连续无跳变。

## 2. 圆角：DWM 不给无重定向窗口做圆角，得自己裁

主窗口靠 `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`（`src/win.rs`）。播放器是
`WS_EX_NOREDIRECTIONBITMAP` 的 DComp 窗口，没有重定向表面，DWM 不裁 —— 所以 beta.7
里是方的。

`src/dcomp/player_window.rs` 现在给**每一层**都挂一个 `IDCompositionRectangleClip`：

* 背景层（f213 的 `PLAYER_BG`）、UI 层：裁到客户区大小，半径 = `12 DIP × scale`；
* 视频层：它自己的 clip 本来就在**换链像素空间**（`apply_geometry` 里已经按
  transform 反算），半径同样除以 `scale_x/scale_y`，屏幕上是同一个 12 DIP；
* 弹幕层：它有自己的、画面大小的 visual，按画面矩形裁同样的半径（否则角上的弹幕
  会画到圆角外面）。

窗口尺寸变化（`WM_SIZE`）、DPI 变化（`WM_DPICHANGED`）、进出全屏都重新下发；
全屏时半径归零（和 DWM 对最大化窗口的处理一致，否则四个角会漏出桌面）。
`corner_radius_px` 有单测（1.0/1.5/2.0 倍缩放、全屏、非法缩放因子）。

日志：`dcomp player corners size=1000x600 radius=12.0 fullscreen=0`。
截图：`docs/f218_player_corners.png`（四角 4× 放大，主窗口放在后面，圆角切口处能
看到后面的壁纸）。

## 3. 皮肤：属性都在，问题是「发布顺序」和「膜太厚」

先说结论：**属性没有缺**。`set_player_backdrop` 一直是每窗口一份地发
`glass-blur`（1024×1024）、`wallpaper` / `wallpaper-light`、`wall-x/wall-y`
（按窗口屏幕位置算，`-60,-60`）、`wallpaper-tile`、`backdrop-blur`、`cards-flat`。
现在这一整行会打出来，可以逐项核对：

```
theme win=player dark=1 glass_blur=1024x1024 wallpaper=1024x1024 wall=(-60,-60) tile=1024
  backdrop_blur=60 cards_flat=0 glass_tint=... bar_fill=... panel_tint=... menu_tint=...
```

真正的两个问题：

1. **膜太厚。** `player-panel-tint` 88 %/90 %、`player-menu-tint` 95 %：采样图一直
   在画，但透不出来，和主窗口的 `card`（70 %/81 %）并排看就是一块死灰。现在两者
   都落到主窗口 `card` 的档位（`#1e1e1eb3 / #ffffffcf`、`#1e1e1eb8 / #ffffffd9`）。
   深色截图里右栏从上到下 `(59,41,66) → (52,46,70) → (51,53,58)`，是壁纸的连续
   渐变，不再是常数。
2. **三块表面根本不是 `GlassPanel`。** 拖动时间读数、插帧提示、进度条预览卡
   （storyboard）、弹幕/画质里的锁定行提示，都是 `Rectangle { background:
   AppTheme.player-menu }` —— 平面色块，压在采样层上面。现在全部改成 `GlassPanel`
   + `tint: AppTheme.player-menu-tint`。`ToastView` 同样改用更薄的 `menu_tint`。
   注意 `scrub_dragging` 那块原来是 `GlassPanel` 但**又写了 `background:`**，等于
   在采样层上盖了一块不透明底，这次一并去掉。

`cards_flat` 也改成进程级一致（`BILI_CARD_FLAT` 由主窗口和播放器窗口读同一个来源），
不会再出现「首页采样、播放器纯色」的 A/B 混搭。

截图：`docs/f218_player_chrome.png`（深色，右栏 + 弹幕弹层 + 控制条）。
